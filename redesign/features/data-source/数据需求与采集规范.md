# 数据需求与采集规范

> 版本: v0.1 | 日期: 2026-09-26 | 状态: 草稿（待评审）
>
> 一句话：盘点项目真正需要的数据，把「每天要采的」收敛为一次收盘数据包；列出表设计中的重复存储、僵尸字段与幂等缺口，给出收敛方向。

## 一、结论先行

1. **每日真正需要外部采集的只有一套「收盘数据包」**（§四，共 8 项），其余数据要么由它派生、要么属事件驱动采集（分析运行时 / 用户操作 / 按需实时）。当前的问题是同一上游数据被 2~5 条链路重复抓取、重复落库。
2. **涨停池「一源五写」**：一次 `get_limit_up_pool` 抓取同时落 5 张表（池明细 + 梯队聚合 + 快照计数 + 周焦点股/板块聚合 + 明日重点 JSON）。梯队表（`market_limit_ladder_snapshot`）全部字段 100% 可由明细表聚合得出。
3. **指数收盘存 3 处且读取口径不互通**：`stock_daily`（指数行）、`market_daily_snapshot`（6 个平铺列）、`analysis_history.context_snapshot`（复盘快照）。预期评分读 `stock_daily` 的 `000300` 行——指数行 code 形态取决于分析时的写法，取不到时**静默退化为基准分 50**，而情绪表里同日 `hs300_chg_pct` 就在旁边。
4. **资讯 4 处存储**：`news_intel`（搜索链路）与 `intelligence_items`（RSS 链路）字段结构高度相似但唯一键口径不同（全局 url vs scope+url），是两套并行未合并的资讯表；外加 `market_focus_events`（打标副本）与 `analysis_history.news_content`（报告快照）。
5. **僵尸字段**：5 张表存在写入恒空/恒 0 的字段（主力/北向资金、60 日新高新低、龙虎榜/机构买入等，无免费数据源，v1 置空后未再实现）；另有字段名与语义漂移（`lifecycle_stage` 实际存"涨停N家"文本）。
6. **幂等缺口**：6 张表无唯一约束，靠应用层查询去重（情绪焦点事件、告警触发、决策信号、分析历史、现金台账等），并发/重放可重复插行。
7. **基础设施层根因**：每次调用 `new DataFetcherManager()`，实例级限流计时器与缓存互不可见——同一分钟多路请求直达上游，「重复采集」在限流上等于未设防。

## 二、项目功能 → 数据需求映射

以消费方倒推需要什么数据（不是先有表再找用途）：

| 功能 | 需要的数据 | 频次 | 现状落库 |
| --- | --- | --- | --- |
| 每日个股分析（`main.py`） | 个股日线 30/60 天、实时行情、筹码、基本面、所属板块、相关新闻 | 每任务 1 次 | `stock_daily`、`news_intel`、`analysis_history`、`fundamental_snapshot` |
| 每日大盘复盘（`--market-review`） | 指数、涨跌统计、板块/概念排行 | 每日 1 次 | `analysis_history`（market_review 行） |
| 大盘情绪页 | 收盘快照 + 池明细 + 盘中实时（指数/涨跌统计） | 收盘 1 次 + 盘中 TTL | `market_daily_snapshot` 等 7 张 |
| 预期管理评分 | 沪深300 当日涨跌幅、个股当日涨跌 | 读库即可 | 应读 `market_daily_snapshot` / `stock_daily` |
| 回测 / 成长页 | 分析历史 + 前向日线 | 读库 + 补日线 | `backtest_results` 等 3 套后验表 |
| 组合持仓估值 | 最新收盘价、汇率 | 读库 + 用户触发 | `portfolio_*` 8 张 |
| 告警 | 实时行情（规则评估） | 周期任务 | `alert_*` 4 张 |
| 聊天 Agent | 按需取数（工具调用） | 事件驱动 | `conversation_*` 5 张 |
| 智能选股 | 实时筛选快照 | 用户触发 | `screening_runs` |

**结论**：日频外部依赖只有 8 项（§四）；个股分析、复盘、情绪页三链路对「指数 + 涨跌统计 + 池」的重复抓取应收敛为一次采集、多处读库。

## 三、数据分层与频次原则

| 层 | 内容 | 频次 | 落库策略 |
| --- | --- | --- | --- |
| **L1 收盘快照层** | §四收盘数据包 | 每交易日 1 次（收盘后定时，非用户触发） | 必落库，按日幂等 upsert |
| **L2 盘中实时层** | 指数/涨跌统计/个股行情实时读数 | 请求驱动 | **不落库**，仅 TTL 缓存（现 60s） |
| **L3 事件驱动层** | 个股分析抓取、用户操作、Agent 工具 | 事件发生时 | 按各自表语义落库 |

- L1 是唯一的定时外部采集入口；L2 永远读缓存不写表；L3 只为自己服务（分析写分析表），**不允许顺手采集市场级日频数据**（当前 market_review 与情绪采集重复抓指数/涨跌统计即违反此条）。
- 当前缺口：L1 无独立调度（GitHub Actions 只跑分析，情绪采集靠用户打开页面触发盘后补采）。

## 四、每日收盘数据包（唯一日采入口）

`collect_daily_snapshot` 一次跑完，顺序与内容：

| # | 数据 | 来源 | 落库 | 消费方 |
| --- | --- | --- | --- | --- |
| 1 | A 股指数收盘（上证/深成/沪深300/上证50/创业板：点位、涨跌幅）+ 沪/深成交额 | `get_main_indices('cn')` 或指数日线链 | `market_daily_snapshot` | 情绪页、复盘、预期评分 |
| 2 | 大盘统计：涨跌家数、涨停/跌停家数、两市成交额 | `get_market_stats` | `market_daily_snapshot` | 情绪页、复盘 |
| 3 | 三类池全量明细（涨停/跌停/炸板，n=500）——**唯一事实源** | `get_limit_up/down/blown_pool(date)` | `market_pool_detail_snapshot` | 梯队、炸板率、焦点、明日重点全部由它派生 |
| 4 | 外盘：美股昨夜 + 韩股 | `get_main_indices('us'/'kr')` | `overseas_summary`（JSON） | 情绪页外盘卡 |
| 5 | 财经日历：**未来 7 天 + 明日，一次拉全窗口** | `get_economic_calendar(date)` | `market_focus_events`(calendar) + `market_tomorrow_focus` | 周/月聚焦、明日重点 |
| 6 | 市场快讯 n=100 → 规则打标 | `get_market_news` | `market_focus_events` | 周/月聚焦事件 |
| 7 | 板块排行 n=8 | `get_sector_rankings` | （当前仅内存使用，按需评估是否入快照） | 采集内计算 |
| 8 | 板块区间日线 | `get_sector_history` | 周期聚合输入 | **仅周/月生成日拉取，非每日** |

**零采集派生数据**（由 #3 明细聚合，禁止再抓上游）：梯队高度分布、炸板率、板块聚集度、晋级候选、焦点股/板块周月聚合、明日重点 stock_watch/sector_watch、prev_limit_up_again/blown（读昨日池明细即可）。

## 五、表设计重复与不规范清单

### A. 重复存储（重复采集的落库面）

| 编号 | 问题 | 建议 |
| --- | --- | --- |
| A1 | 涨停池一源五写：`market_pool_detail_snapshot`(39) 为事实源，`market_limit_ladder_snapshot`(38) 全字段可聚合推导，`market_daily_snapshot` 计数列、`market_focus_stocks/sectors`(41/42) 周期聚合、`market_tomorrow_focus`(43) JSON 副本 | 保留 39 为唯一事实源；38 重定义为**派生读缓存**（与 39 同一聚合函数、同批事务生成，文档标注 derived）；41/42 保留（跨日聚合有真实成本）；43 保留（含日历/AI 语义），JSON 副本注明「生成时点快照」 |
| A2 | 指数收盘 3 处存：`stock_daily` 指数行 / `market_daily_snapshot` 平铺列 / `context_snapshot` | `market_daily_snapshot` 为指数收盘唯一事实；`stock_daily` 指数行保留（分析需要 MA 链路）；`context_snapshot` 保持快照语义不改 |
| A3 | 读取口径不互通：预期评分读 `stock_daily` 的 `000300` 行，缺失时静默给基准分 50 | **评分改读 `market_daily_snapshot.hs300_chg_pct`**（P0，修正确性） |
| A4 | 资讯 4 处存：`news_intel` 与 `intelligence_items` 结构近乎相同、唯一键口径不一 | 中期合并为一张资讯表（scope 化唯一键 + provider 区分）；短期先统一字段命名，`market_focus_events`（打标语义）与 `news_content`（报告快照）保留 |
| A5 | 大盘统计双链路：情绪采集与 market_review 各抓一次 `get_main_indices` + `get_market_stats` | 复盘改读当日 `market_daily_snapshot`（15:05 后运行天然可读；盘中运行回退实时） |
| A6 | 三套平行后验体系：`backtest_results` / `decision_signal_outcomes` / `skill_opinion_outcomes` 结构近乎相同 | 长期统一评估引擎与表形状；短期不动（稳定性优先），仅标注 |

### B. 僵尸字段（写入恒空/恒 0，处置三选一：接源 / 删列 / 标注）

| 表 | 字段 | 现状 | 建议 |
| --- | --- | --- | --- |
| `market_daily_snapshot` | main_inflow、north_inflow、new_high_60d、new_low_60d | 采集硬编码 None（无免费源） | 删列；将来有源再加（加列成本 = 一次 ALTER） |
| `market_limit_ladder_snapshot` | prev_limit_up_blown、prev_limit_up_down | 置 None | 可由昨日池明细推导 → 实现或删 |
| `market_focus_stocks` | dragon_tiger、inst_buy（恒 0）、main_inflow、turnover_rate（None） | 硬编码 | 列随 A4/A1 收敛一并删 |
| `market_focus_sectors` | main_inflow（None）；`lifecycle_stage` 存"涨停N家"文本、`lifecycle_day` 存最高连板数 | 语义漂移 | 删 main_inflow；`lifecycle_*` 重命名为 `limit_up_summary` / `max_boards` |
| `llm_usage` | tokenizer_name/version 停写兼容列 | — | 维持现状（有注释），不再扩散 |

### C. 幂等缺口（无唯一约束，仅应用层查重）

| 表 | 现状去重键 | 建议 |
| --- | --- | --- |
| `market_focus_events` | (event_date, scope, title) 应用层查重 | 补 SQLite 唯一索引 |
| `alert_triggers` | (rule_id, target, status, data_timestamp, data_source) | 补唯一索引（含 status 需斟酌，可用部分索引或去重列） |
| `decision_signals` | 复杂 create_if_absent + relaxed 合并 | 保持应用层合并语义，补防重唯一索引（source_report_id 或 trace 维度） |
| `analysis_history` | 无任何键，query 重试追加重复行 | 评估 (query_id, report_type, trade_date) 唯一性 |
| `portfolio_cash_ledger` / `corporate_actions` | 无幂等键，重复提交重复入账 | 客户端 uid + 唯一索引 |
| `user_expectations` | 唯一键 `(target_date)` 不含 market 列，与多市场字段语义冲突 | 约束改 `(market, target_date)` |

### D. 未接线能力（定义了但无调用入口）

1. `backfill_recent_snapshots()` 无 API/CLI/调度入口（文档已宣告）——挂到 CLI 或采集端点参数。
2. `skill_opinion_outcomes` / `decision_signal_outcomes` 评估无定时任务（仅 API 手动触发）——应挂进每日收盘后流程（L1 尾部追加评估步骤）。
3. L1 收盘采集本身无调度，靠用户打开页面触发盘后补采——挂 `main.py --schedule` 或 GitHub Actions 定时。
4. `collect_daily_snapshot` 中 `is_complete=1` 先落库、池明细后写：中途崩溃重启会被"完整"标记跳过，快照完整但明细缺失——改为**先明细后聚合最后置 complete**。

## 六、采集规范（新增/改造数据面时必须遵守）

1. **单一日采入口**：市场级日频数据只允许在 `collect_daily_snapshot` 采集；其他链路读库，盘中回退实时（L2）。
2. **明细为事实源**：派生表/字段必须与明细由同一聚合函数、同批事务生成，并在表注释标注 derived；禁止各自独立计算同一指标。
3. **落库必幂等**：日频表必须有 SQLite 唯一约束（trade_date 或复合键）+ upsert/delete+insert；仅应用层查重视为缺陷。
4. **僵尸字段零容忍**：新表不允许出现无数据源的占位列；存量字段按「接源/删列/标注」三选一处置。
5. **读取走单一入口**：同一数据全仓库只有一个读取函数（如沪深300 当日涨跌幅只读 `market_daily_snapshot`），新代码禁止绕过。
6. **数据源基础设施共享**：FetcherManager 的限流计时器、缓存必须跨调用方共享（模块级单例或容器注入）；禁止每个 service `new Manager()` 导致限流失效。
7. **实时不落库**：L2 实时读数只允许 TTL 缓存；把实时数据写表必须有明确的快照语义（如 `market_pool_detail_snapshot` 之于盘中兜底）。
8. **时序可续采**：采集流程先明细、后聚合、最后置完成标记；任何一步失败重跑可续，不允许用完成标记掩盖半截数据。
